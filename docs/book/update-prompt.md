# wjsm 手册更新提示词

你负责维护 `docs/book/` 下的单一 mdBook。它包含两个严格分区：面向使用者的“用户手册”和面向项目开发者的“内部手册”。请以 `.version` 所记录的 wjsm 代码提交为基线，将两个分区完整同步到目标代码提交。

## 固定结构

- 只保留一个 mdBook 入口：`docs/book/book.toml`。
- 首页 `docs/book/src/README.md` 必须同时提供用户手册和内部手册的入口。
- 用户内容位于 `docs/book/src/user/`，并在 `SUMMARY.md` 中排在前面。
- 内部内容位于 `docs/book/src/internals/`，以独立 Part 和分隔线与用户内容隔开，并整体排在最后。
- 不要建立第二个 `book.toml`，不要让两个分区各自拥有构建、搜索或导航入口。
- 章节路径是公开 URL 的一部分；除非确有结构性必要，不要随意移动或重命名已经发布的章节。

## 跨手册引用

- 用户手册章节若存在对应的内部设计、实现规范或不变量说明，必须在章末增加 `## 深入了解`，使用相对链接指向相关内部手册章节。
- 引用普通章节时链接对应的 `.md` 源文件；引用以 `README.md` 为源码的目录入口时使用对应的 `index.html` 输出路径。mdBook 0.5 会把正文中的 `README.md` 改写成不存在的 `README.html`。
- 一个用户章节可以引用多个内部章节；链接文字必须说明可继续了解的具体主题，不能只写“更多信息”。
- “深入了解”是可选的深挖路径。用户完成安装、配置、命令操作和故障排查不得依赖阅读内部手册。
- 不要在用户正文中复制大段内部实现；用户可观察行为留在用户手册，实现 owner、数据流、ABI 和不变量留在内部手册，通过链接连接。
- 内部章节涉及公开行为时可以反向链接到对应用户章节，避免重复维护用法和示例。
- 新增、移动或删除章节时必须同步检查这些跨分区链接，并通过整书构建验证相对路径。

推荐的用户章节结尾格式：

```markdown
## 深入了解

- [WASM Import、Export 与主模块 ABI](../../internals/backend/imports-exports-and-abi.md)
- [实例化与执行生命周期](../../internals/host-runtime/instantiation-and-lifecycle.md)
```

应根据当前用户章节的目录深度计算真实相对路径，不能机械复制示例。

## 版本锚点

1. 读取 `docs/book/.version`，其内容必须是一个带换行结尾的 40 位小写 Git commit ID。
2. 验证该提交存在，并检查从锚点到目标提交的提交记录和完整差异。
3. `.version` 锚定的是“手册正文已经覆盖到的 wjsm 代码版本”，不是文档提交自身。Git 提交不能可靠地在自身内容中保存自己的 ID；因此，目标代码提交必须先存在，再由后续文档提交将 `.version` 指向它。
4. 未提交的代码改动没有可用的稳定锚点。可以为它们同步手册，但不得声称 `.version` 已锚定这些改动。
5. 只有两个分区都完成同步且构建验证通过后，才能把 `.version` 更新为目标代码提交的完整 ID。不要提前更新。

建议先执行并审阅：

```bash
anchor="$(tr -d '\r\n' < docs/book/.version)"
git cat-file -e "${anchor}^{commit}"
git log --oneline --decorate "${anchor}..HEAD"
git diff --stat "${anchor}..HEAD"
git diff --name-status "${anchor}..HEAD"
```

随后按受影响文件继续读取完整 diff、调用链、配置 owner、测试和 ADR；不要只依据提交标题更新文档。

## 事实来源

按以下优先级核实事实，不要凭记忆补写：

1. 当前源码、Cargo 清单、生成脚本与命令实际输出。
2. 覆盖对应行为的 fixture、快照、crate 测试和 test262 配置。
3. `docs/adr/` 中仍生效的架构决策；被后续 ADR 取代的内容只用于理解历史。
4. ECMAScript、Node.js、WebAssembly、Wasmtime 与 mdBook 的官方规范或文档。
5. 仓库中的其他说明文档；若与代码或生效 ADR 冲突，以 owner 为准并同步修正相关手册。

涉及“谁调用谁”“数据如何流动”“修改会影响谁”时，先使用代码图定位入口、调用路径和影响范围，再读取确切源码。涉及 CLI 时，以 Clap 参数模型和实际 `wjsm --help`/子命令 `--help` 输出为准。涉及环境变量、配置键或 Cargo feature 时，必须从其解析与优先级 owner 逐项核对。

## 更新流程

1. 确定目标代码提交，验证 `.version` 基线，并列出基线到目标之间所有行为、接口、配置、架构和兼容性变化。
2. 建立“代码变化 → 用户手册章节 → 内部手册章节 → 跨手册链接 → 验证证据”的覆盖表，不能只更新其中一个分区。
3. 先更新用户手册：说明用户可观察到的用途、安装、命令、配置、环境变量、输入输出、兼容性、限制、工作流和故障排查；在存在对应内部内容时添加“深入了解”。不要把实现细节当作使用说明。
4. 再更新内部手册：解释变化的目的、owner、端到端数据流、关键类型和函数、跨 crate 契约、ABI、内存布局、不变量、并发/GC 约束、失败模式、测试与扩展方式，并核对所有来自用户手册的引用目标。
5. 同步 `src/SUMMARY.md`。新增章节必须放入正确分区；删除功能时应删除或改写失效章节，而不是保留“已弃用”空壳。
6. 检查两个分区之间的术语、默认值、命令名、配置优先级、兼容性状态和链接是否一致。共享事实只能有一个明确 owner；另一处使用简要说明和链接，避免复制后漂移。
7. 实际运行手册中的命令和示例。对 JS/TS 示例使用 wjsm 对应命令验证，不要用 `mdbook test` 冒充 JavaScript 语义验证。
8. 构建整本书并处理所有警告或错误：

   ```bash
   mdbook build docs/book --dest-dir /tmp/wjsm-mdbook
   ```

9. 构建与行为验证都通过后，将 `.version` 更新为目标代码提交的完整 ID，并再次确认其可由 Git 解析。

## 用户手册覆盖要求

必须持续核对并覆盖：

- 项目定位、适用场景、执行模型、安装和升级。
- 所有公开 CLI 子命令、全局选项、输入方式、配置文件与优先级。
- 所有面向用户的环境变量、默认值、可选值、相互覆盖关系和平台差异。
- JavaScript/TypeScript 支持、ESM/CommonJS、包解析、npm 包和 Node.js 兼容范围。
- GC、堆与影子栈、启动快照、缓存、Inspector、文件系统与网络能力。
- WASM 输出、宿主要求、标准流、退出码、诊断、资源边界和安全边界。
- 可复现的常用工作流、故障排查、功能矩阵和术语。
- 每个存在内部对应主题的用户章节都必须提供准确、可构建的“深入了解”链接。

不得把尚未实现、仅有 stub、测试专用或内部隐藏的能力写成公开功能。实验性能力必须明确标出状态和约束。

## 内部手册覆盖要求

必须持续核对并覆盖：

- 解析 → 语义 Lowering → IR → 模块 Bundling → WASM 编译 → Host 实例化与执行的完整流水线。
- 每个 workspace crate 的职责、公共 API、依赖方向和单一事实来源。
- 作用域、Hoisting、TDZ、早期错误、CFG、Instruction、值表示和稳定 IR dump。
- 多后端边界、WASM ABI、Support 模块、数据段、函数表、槽位活跃性和 GC Spill。
- Host trait、ExecContext、Builtins、RuntimeState、Realm、模块加载和 Node.js Built-in 组织。
- ManagedHeap、Memory64、Handle Table、对象布局、根、屏障以及 Mark-Sweep/G1/ZGC 的并发不变量。
- Bootstrap、嵌入工件、Support cwasm、启动快照、格式版本、重定位和 ABI hash。
- Eval、`node:vm`、异步调度、`node:async_hooks`、Worker、Inspector、网络/TLS 等运行时子系统。
- CLI/配置合并、缓存、构建脚本、生成工件、Cargo feature/profile、发布与兼容性边界。
- Fixture、语义快照、Backend/Runtime 测试、test262、GC benchmark、调试和性能证据。
- 新增语言功能、IR、Builtin、Host Import、Node 模块，以及修改 ABI、快照、GC 时的跨层步骤。

内部手册必须解释“为什么”“谁拥有”“如何流动”“哪些不变量不能破坏”，不能退化为文件列表或源码复述。

## 写作与完成标准

- 正文使用中文；API、类型、函数、命令、协议和规范名称保留原文。
- 每章从读者目标出发，给出足够上下文、准确示例、边界条件和相关章节链接。
- 命令、默认值、数字、标签、ABI、环境变量和兼容性结论必须有当前代码证据。
- 首次填充骨架时，空章节必须根据事实来源完成后才能声称整本手册已完成；后续增量更新至少覆盖全部受影响章节，并检查全局一致性。
- 不保留 TODO、占位文本、无效链接、重复 owner、失效兼容路径或猜测性描述。
- 构建产物不得提交到 `docs/book/book/`；验证输出写入 `/tmp`。
- 最终报告应列出目标代码提交、更新章节、关键事实来源、实际运行的验证命令和仍然存在的明确限制。
